\section{Inköpslistor med klasser}

I detta avsnitt ska vi utforska hur klasser kan användas för att hantera 
inköpslistor. Detta är ett praktiskt exempel som visar hur vi kan använda 
klasser för att organisera data och funktionalitet på ett strukturerat sätt.

\subsection{Problemformulering}

\begin{exercise}
  Skriv ett program som hanterar en inköpslista. Programmet ska kunna:
  \begin{itemize}
    \item Lägga till saker på listan
    \item Lista alla varor
    \item Bocka av enskilda saker
    \item Ta bort alla avbockade saker
  \end{itemize}
  Vi ska kunna ha flera olika inköpslistor (exempelvis en för mat, en för

Vi kan använda \emph{komposition} för att lägga till adresser. Komposition

föredra framför att lägga till många attribut i en enda klass.

\end{frame}

Nu kan vi uppdatera Person-klassen för att använda Address-klassen:

\begin{frame}[fragile]
  \begin{example}[Person med adress]
    Komposition av Address-objekt:
    \inputminted[linenos,firstline=21,lastline=28]{python}{examples/bank.py}
  \end{example}
\end{frame}

\begin{exercise}
  Vad är fördelarna med att använda komposition (en separat Address-klass) 
  istället för att lägga till street, city och zipcode som attribut direkt 
  i Person-klassen?
\end{exercise}

Fördelarna med komposition inkluderar:
\begin{itemize}
  \item \textbf{Återanvändbarhet}: Address-klassen kan användas i andra 
    sammanhang (företag, skolor, etc.).
  \item \textbf{Modularitet}: Adresslogik kan ändras utan att påverka 
    Person-klassen.
  \item \textbf{Tydlighet}: Det är tydligt att adressen är en sammanhängande 
    enhet.
  \item \textbf{Validering}: Vi kan lägga till validering i Address-klassen 
    (t.ex. kontrollera att postnumret har rätt format).
\end{itemize}

\subsection{Bankkontot}

\begin{exercise}
  Nu ska vi skapa själva bankkontot. Vilka attribut och metoder behöver 
  ett bankkonto ha?
\end{exercise}

Ett bankkonto behöver hålla reda på vem som äger kontot (en Person) och hur 
mycket pengar som finns på kontot (saldot). Vi behöver också metoder för att 
sätta in och ta ut pengar. Uttag ska bara tillåtas om det finns tillräckligt 
med pengar på kontot.

\begin{frame}[fragile]
  \begin{example}[Bankkontoklass]
    Ägare, saldo och insättning:
    \begin{minted}[fontsize=\small]{python}
class BankAccount:
    def __init__(self, owner, initial_balance=0):
        self.owner = owner  # Ett Person-objekt
        self.balance = initial_balance
    
    def deposit(self, amount):
        if amount > 0:
            self.balance += amount
            return True
        return False
    \end{minted}
  \end{example}
\end{frame}

Här ser vi ett annat exempel på komposition: ett \mintinline{python}{BankAccount} 
innehåller ett \mintinline{python}{Person}-objekt.

\begin{exercise}
  Varför returnerar \mintinline{python}{deposit}-metoden \mintinline{python}{True} 
  eller \mintinline{python}{False}?
\end{exercise}

Genom att returnera en boolean kan anroparen veta om insättningen lyckades. 
Detta gör det möjligt att hantera fel och ge användaren feedback om 
insättningen inte kunde genomföras (till exempel om beloppet var negativt).

\begin{frame}[fragile]
  \begin{example}[Ta ut pengar från kontot]
    Uttag med validering:
    \begin{minted}{python}
    def withdraw(self, amount):
        if 0 < amount <= self.balance:
            self.balance -= amount
            return True
        return False
    
    def __str__(self):
        return f"Konto: {self.owner.name}\nSaldo: {self.balance} kr"
    \end{minted}
  \end{example}
\end{frame}

Metoden \mintinline{python}{withdraw} kontrollerar att beloppet är positivt 
och att det finns tillräckligt med pengar på kontot innan uttaget görs.

\begin{exercise}
  Vad händer om vi försöker ta ut mer pengar än vad som finns på kontot?
  Kan du tänka dig andra sätt att hantera detta?
\end{exercise}

\subsection{Arv: Medborgare med personnummer}

Nu ska vi se hur \emph{arv} kan användas för att utöka funktionalitet. 
Arv innebär att vi skapar en ny klass baserad på en befintlig klass.

\begin{exercise}

  personnummer, skulle du:
  \begin{enumerate}[label=\alph*)]
    \item Lägga till personnummer som attribut i Person-klassen?
    \item Skapa en helt ny klass med all kod duplicerad?
    \item Använda arv för att skapa en Citizen-klass som ärver från Person?
  \end{enumerate}
  Motivera ditt val.
\end{exercise}

Vi använder arv för att skapa en \mintinline{python}{Citizen}-klass som ärver 
från \mintinline{python}{Person}. Detta betyder att \mintinline{python}{Citizen} 
får alla attribut och metoder från \mintinline{python}{Person}, men kan lägga 
till eller ändra funktionalitet.

\begin{exercise}
  Vad gör \mintinline{python}{super().__init__(name, age, address)}?

\mintinline{python}{super()} ger oss tillgång till föräldraklassen. Genom att

\section{Sammanfattning}

I detta kapitel har vi utforskat praktiska tillämpningar av klasser genom 
två omfattande exempel: inköpslistor och ett banksystem.

\subsection{Vad har vi lärt oss?}

Genom inköpslistexemplet såg vi:
\begin{itemize}
  \item Hur klasser kan organisera relaterad data och funktionalitet
  \item Hur vi kan använda listor av objekt från våra egna klasser
  \item Hur metoder kan kapsla in logik för att manipulera data
\end{itemize}

Genom banksystemet utforskade vi:
\begin{itemize}
  \item \textbf{Komposition}: Bygga komplexa system från enklare delar 
    (Address i Person, Person i BankAccount)
  \item \textbf{Arv}: Utöka funktionalitet genom att skapa specialiserade 
    klasser (Citizen från Person)
  \item \textbf{Polymorfism}: Använda subklasser där basklasser förväntas
\end{itemize}

\subsection{Designprinciper}

\begin{exercise}
  Reflektera över de exempel vi har sett. Vilka designprinciper har vi 
  tillämpat? Hur har dessa principer gjort koden bättre?
\end{exercise}

Viktiga designprinciper vi har sett:

\begin{description}
  \item[Inkapsling] Håll data och metoder tillsammans. Varje klass har 
    tydligt definierad funktionalitet.
  \item[Abstraktion] Dölj komplexitet bakom enkla gränssnitt. Användaren av 
    en klass behöver inte veta hur den fungerar invändigt.
  \item[Återanvändbarhet] Skapa generella, återanvändbara klasser. Address 
    kan användas i många sammanhang, inte bara för personer.
  \item[Moduläritet] Dela upp problem i mindre, hanterbara delar. Varje klass 
    har ett tydligt ansvar.
  \item[Komposition över arv] Föredra komposition (innehålla objekt) framför 
    arv när möjligt. Det ger mer flexibilitet.
\end{description}

\subsection{När ska vi använda klasser?}

\begin{exercise}
  När är det lämpligt att skapa en klass? När räcker det med enklare 
  datastrukturer som listor och uppslagslistor?
\end{exercise}

Klasser är lämpliga när:
\begin{itemize}
  \item Du har relaterad data som hör ihop logiskt (person med namn och adress)
  \item Du behöver metoder som arbetar med denna data
  \item Du vill inkapsla och skydda data
  \item Du har komplexa objekt som interagerar med varandra
  \item Du vill återanvända kod i olika sammanhang
\end{itemize}

Enklare strukturer räcker när:
\begin{itemize}
  \item Du har enkel, temporär data
  \item Ingen komplex logik behövs
  \item Data bara ska lagras och läsas, inte manipuleras
\end{itemize}

\subsection{Komposition vs Arv}

En viktig avvägning i objektorienterad design är när man ska använda 
komposition respektive arv.

\begin{exercise}
  I vårt bankexempel: Varför använde vi komposition för Address och Person, 
  men arv för Citizen?
\end{exercise}

\begin{frame}[fragile]
  \begin{block}{Komposition (has-a)}
    En klass \emph{innehåller} ett objekt av en annan klass.
    \begin{itemize}
      \item Person \emph{har} en Address
      \item BankAccount \emph{har} en Person
    \end{itemize}
    
    Fördelar:
    \begin{itemize}
      \item Mer flexibelt
      \item Lättare att ändra vid körtid
      \item Tydliga relationer
    \end{itemize}
  \end{block}
\end{frame}

\begin{frame}[fragile]
  \begin{block}{Arv (is-a)}
    En klass \emph{är en specialisering} av en annan klass.
    \begin{itemize}
      \item Citizen \emph{är en} Person (med extra information)
    \end{itemize}
    
    Fördelar:
    \begin{itemize}
      \item Återanvänder kod från basklassen
      \item Polymorfism: kan användas där basklassen förväntas
      \item Tydlig hierarkisk relation
    \end{itemize}
    
    Nackdelar:
    \begin{itemize}
      \item Starkare koppling mellan klasser
      \item Svårare att ändra senare
    \end{itemize}
  \end{block}
\end{frame}

Tumregel: Föredra komposition, använd arv när du verkligen har en 
is-a-relation.
