\section{Två exempel}

\ltnote{%
  \textbf{Learning Objectives addressed in this section:}
  \begin{enumerate}
    \item LO1: Förklara skillnaden mellan en klass och ett objekt
    \item LO2: Skapa klasser med attribut och metoder
    \item LO5: Använda inkapsling för att skydda data
  \end{enumerate}

  \textbf{Variation Pattern: Contrast}

  \textbf{What varies}: Implementation approach (dict-based vs class-based)

  \textbf{What remains invariant}: The problem (phonebook/contacts
  management) and the functionality (store and retrieve information)

  \textbf{Critical aspects to discern}:
  \begin{itemize}
    \item \textbf{LO1}: By seeing the same problem solved with and without
      classes, students can discern what a class IS versus what it is NOT.
    \item \textbf{LO2}: The contrast shows that classes provide structure
      through attributes and methods, making the code more organized.
    \item \textbf{LO5}: The comparison reveals how classes enable
      encapsulation (private attributes, controlled access), which is
      absent in the dict-based solution.
  \end{itemize}

  \textbf{Why this variation works}: Following Marton \& Pang (2006),
  we vary the implementation approach while keeping the problem invariant.
  This makes the BENEFITS of classes discernible because students can see
  EXACTLY what changes (code structure, error handling, data safety) when
  introducing classes. Starting with a familiar dict-based solution
  creates a concrete reference point for comparison.

  \textbf{Pedagogical sequence}: We follow the contrast pattern by first
  showing what classes are NOT (the dict approach) before showing what
  they ARE (the class approach). This adheres to variation theory's
  principle that ``to discern something, you must experience what it is
  versus what it is not.''
}

I det här kapitlet kommer vi att utforska objektorienterad programmering
genom att jämföra två olika sätt att lösa samma problem: med och utan
klasser. Genom att se skillnaderna konkret kan vi bättre förstå vilka
fördelar klasser erbjuder.

\subsection{Utan klasser}

Vi börjar med att titta på ett enkelt program för en telefonbok, skrivet
utan att använda klasser.
\begin{exercise}
  Skriv ett program som lagrar ett par telefonnummer för några personer och
  låter användaren hämta dem.
  Programmet ska kunna:
  \begin{itemize}
    \item Visa alla kontaktnamn i telefonboken.
    \item Be användaren skriva ett namn så skriver programmet ut motsvarande
      telefonnummer.
    \item Fortsätta fråga efter namn tills användaren trycker Enter på en tom rad.
      Då avslutar programmet.
  \end{itemize}
\end{exercise}

\ltnote{%
  Following try-first pedagogy, we ask students to attempt implementing
  the phonebook themselves before showing our solution. This activates
  their prior knowledge of dicts and creates a knowledge gap that makes
  the subsequent contrast with classes more meaningful. When they later
  see our dict-based solution AND the class-based solution, they can
  compare all three approaches (their own, ours with dicts, ours with
  classes), enriching the contrast pattern.
}

Vi kan använda en uppslagslista för att lagra namn och telefonnummer.

\begin{frame}[fragile]
  phonebook.py \hrulefill
  \inputminted[linenos]{python}{examples/phonebook.py}
\end{frame}

Detta är en ganska enkel lösning. Men vad händer om vi vill lagra mer
information om varje person? Kanske vill vi ha både telefonnummer och
adress?

\ltnote{%
  \textbf{Variation Pattern: Separation}

  We now vary the COMPLEXITY of the data structure (simple string values
  $\rightarrow$ nested dicts with multiple fields) while keeping the
  dict-based approach invariant. This separation helps students discern
  that the dict approach has inherent limitations that become visible
  only when requirements grow.

  \textbf{Relation to Learning Objectives}: This prepares students for
  LO5 (encapsulation) by showing the PAIN POINTS of unencapsulated data:
  no structure enforcement, error-prone key access, lack of validation.
}

\begin{exercise}
  Hur skulle du modifiera programmet ovan för att även lagra adresser?
  Tänk igenom strukturen innan du fortsätter läsa.
\end{exercise}

\ltnote{%
  Try-first pedagogy again: Students predict/attempt before seeing the
  nested dict solution. This creates productive struggle that highlights
  the design challenges, making them more receptive to the class-based
  solution later.
}

Ett första försök skulle kunna vara att använda en nästlad uppslagslista, 
där varje person får en uppslagslista med olika fält. Låt oss titta på hur det 
kan se ut (\texttt{phonebook.py} hade vi tidigare, vårt förbättrade program 
lägger vi i \texttt{contacts.py}):

Nu har vi en mer komplicerad datastruktur. Varje person representeras av 
en uppslagslista med nycklarna \mintinline{python}{"phone"} och \mintinline{python}{"address"}. 
Notera att inte alla personer har alla fält ifyllda.

\begin{exercise}
  Vad händer om du försöker läsa ett fält som inte finns för en person? 
  Vilket fel kommer du att få?
\end{exercise}

Svaret är att du får ett \mintinline{python}{KeyError}. Detta måste vi hantera när vi 
läser informationen. Låt oss se hur koden för att läsa informationen blir:

\begin{frame}[fragile]

  \vspace{0.5em}
  contacts.py \hrulefill
  \inputminted[linenos,firstline=25,lastline=35]{python}{examples/contacts.py}

Som du ser blev koden ganska omständlig. Vi måste använda \mintinline{python}{try-except} 
för varje fält vi vill läsa, eftersom vi inte vet om fältet finns. Detta blir 
snabbt svårläst och repetitivt.

\begin{exercise}
  Vilka problem kan du se med denna approach? Tänk på:
  \begin{itemize}
    \item Vad händer om du skriver fel nyckelnamn i uppslagslistan?
    \item Hur vet andra programmerare vilka fält som finns tillgängliga?
    \item Vad händer om du vill lägga till validering (t.ex. kontrollera
          att telefonnumret har rätt format)?
  \end{itemize}
\end{exercise}

\ltnote{%
  Try-first: Students identify problems themselves before we explicitly
  state them. This critical reflection on the dict approach prepares
  the ground for understanding WHY classes are beneficial. Students who
  discover problems themselves are more motivated to learn the solution.

  \textbf{Completing the Contrast pattern}: We have now shown:
  \begin{enumerate}
    \item Simple dict approach (works)
    \item Complex dict approach (problematic)
  \end{enumerate}
  Next, we introduce classes to contrast both of these. The pain points
  become the learning motivation.
}

Låt oss nu se hur klasser kan hjälpa oss att lösa dessa problem på ett
mer elegant och strukturerat sätt.

\subsection{Med klasser}

\ltnote{%
  \textbf{Contrast Pattern (second half)}: Now we show what classes ARE
  by contrasting them with what they are NOT (the dict approaches shown
  earlier).

  \textbf{Relation to Learning Objectives}:
  \begin{itemize}
    \item \textbf{LO1 (class vs object)}: The code will show both the
      class definition AND object creation, making the distinction clear
      through contrast.
    \item \textbf{LO2 (attributes and methods)}: We see structured
      attributes (vs loose dict keys) and methods (vs standalone functions).
    \item \textbf{LO5 (encapsulation)}: Private attributes with
      \mintinline{python}{__} contrast with the open dict access shown earlier.
  \end{itemize}

  \textbf{What remains invariant}: The problem domain (contact management)
  and the required functionality. This invariance is crucial---by keeping
  the WHAT constant, students can focus on discerning the HOW (the
  implementation approach).
}

Nu ska vi se samma funktionalitet implementerad med hjälp av klasser.
Istället för att använda nästlade uppslagslistor skapar vi en
\mintinline{python}{Person}-klass som innehåller all information om en person.

Här har vi definierat en \mintinline{python}{Person}-klass med en

  Varför tror du att attributen börjar med dubbla understreck 
  (\mintinline{python}{__})? Vad betyder detta i Python?
\end{exercise}

De dubbla understrecken gör attributen privata, vilket innebär att de 
inte kan nås direkt från utsidan av klassen. Detta kallas inkapsling 
(encapsulation) och är en viktig princip i objektorienterad programmering.

\begin{exercise}
  Jämför koden för att skapa personer i de två exemplen. Vilka skillnader ser 
  du? Vilket sätt tycker du är tydligare och varför?
\end{exercise}

Noterar du att koden för att skapa personer är tydligare med klasser? 
Vi ser direkt vilka argument som behövs, och i vilken ordning. Med 
uppslagslistor är det lätt att göra fel eller glömma ett fält.
Dessutom ser vi här att datat gäller en person 
(\mintinline{python}{person.Person}).

metoder för att hämta information.

\begin{exercise}
  Hur tror du vi kan läsa information från en 
  \mintinline{python}{Person}-instans?
  Tänk på hur vi gjorde det med uppslagslistor innan:
  \mintinline{python}{phonebook["adam"]["phone"]}.
\end{exercise}

Vi behöver definiera metoder (exempelvis \mintinline{python}{get_name} nedan) 
som låter oss läsa ut attributen.

\begin{frame}[fragile]
  person.py \hrulefill
  \inputminted[linenos,firstline=3,lastline=4]{python}{examples/person.py}
  \dots
  \inputminted[autogobble=false,linenos,firstline=17,lastline=23]{python}{examples/person.py}
  \dots
  \inputminted[autogobble=false,linenos,firstline=65,lastline=70]{python}{examples/person.py}
\end{frame}

Detta är ett exempel på inkapsling.
Vi har attribut,
\mintinline{python}{__first_name} och
\mintinline{python}{__last_name},
som vi kan läsa ut med en metod \mintinline{python}{get_name()}.
Men vi kan inte komma åt attributen direkt utanför klassen.

Vi får skriva liknande metoder för de andra attributen.

\begin{exercise}
  Varför tror du det är bra att inte kunna komma åt attributen direkt? Vad 
  skulle kunna gå fel om vi tillät det?
\end{exercise}

Genom att använda metoder för att läsa och skriva attribut kan vi kontrollera 
hur data hanteras. Vi kan lägga till validering, loggning, eller andra 
funktioner utan att ändra hur användare av klassen interagerar med den.
Vi kan också förhindra att en programmerare oavsiktligt ändrar ett attribut på 
ett sätt som bryter klassens interna logik.
Det förhindrar många möjliga buggar att uppstå.

Här ser vi metoder som \mintinline{python}{get_name()} och 
\mintinline{python}{__str__()}.

\begin{exercise}
  Vad tror du att \mintinline{python}{__str__()}-metoden gör?
  Hur skiljer den sig från \mintinline{python}{get_name()}?
\end{exercise}

Dundermetoden \mintinline{python}{__str__()} är en speciell metod som Python 
anropar automatiskt när vi försöker konvertera objektet till en sträng 
(exempelvis med \mintinline{python}{print()}) eller \mintinline{python}{str()}.

\begin{exercise}
  Varför har metoden \mintinline{python}{__str__()} dubbla understreck 
  både före och efter namnet? Vad tror du detta indikerar?
\end{exercise}

Metoder med dubbla understreck på båda sidor kallas dundermetoder,
\enquote{\foreignlanguage{english}{magic methods}} eller 
\enquote{\foreignlanguage{english}{dunder methods}} på engelska.
Dunder är an sammandragning av orden \foreignlanguage{english}{double 
underscore}.
De har speciell betydelse i Python och anropas \emph{automatiskt} i vissa 
situationer.

Vilken skillnad! Med klasser behöver vi inte hantera \mintinline{python}{KeyError} 
eller kontrollera om fält finns. Metoderna \mintinline{python}{get_phone()} och 
\mintinline{python}{get_address()} garanterar att vi alltid får ett värde

\section{Klasser och objekt}

\ltnote{%
  \textbf{Learning Objective}: LO1 (Förklara skillnaden mellan en klass
  och ett objekt)

  \textbf{Variation Pattern: Contrast}

  \textbf{What varies}: The concept (class vs object)

  \textbf{What remains invariant}: The context (Person example from
  previous section)

  \textbf{Critical aspect to discern}: The distinction between the
  blueprint/specification (class) and the concrete instances (objects).

  \textbf{Why this works}: Students have just seen both class definition
  (\mintinline{python}{class Person:}) and object creation
  (\mintinline{python}{person = Person(...)}). Now we explicitly
  articulate the distinction. The concrete code examples provide the
  grounding for abstract concept formation.

  \textbf{Pedagogical approach}: Try-first (students formulate their own
  definitions) followed by formal definitions. This helps them construct
  understanding actively rather than passively receiving it.
}

Nu har vi sett ett praktiskt exempel. Låt oss definiera begreppen klass och
objekt.

\begin{exercise}
  Vad är en klass och vad är ett objekt?
  Varför vi behöver två olika begrepp i överhuvudtaget?
  Försök att formulera dina egna definitioner innan du fortsätter läsa.
\end{exercise}

I objektorienterad programmering är det viktigt att förstå skillnaden mellan en 
klass och ett objekt.
\begin{description}
  \item[Objekt] är instanser av klasser.
  \item[Klasser] är ritningarna, specifikationerna.
\end{description}

Klassen är som ritningen av huset: den beskriver hur huset ska se ut, vilka rum 
och färger det ska ha, etc. Objekten är de faktiska husen som byggs enligt 
ritningen. Du kan bygga många hus (objekt) från samma ritning (klass), och 
varje hus kan ha olika färger, inredning osv., men grundstrukturen är densamma.

Klassen beskriver vilka data som ska vara med.
Objekten som skapas från klassen innehåller den faktiska datan, själva värdena.

\begin{frame}[fragile]
  \begin{onlyenv}<presentation>
  \begin{block}{Klass}
    \begin{itemize}
      \item En klass är en ritning eller specifikation för ett objekt.
    \end{itemize}
  \end{block}
\end{onlyenv}

  \begin{minted}{python}
    class Class:
      def __init__(self, something):
        self.__attribute = something

      def method(self):
        return self.__attribute
  \end{minted}
\end{frame}

I kodexemplet ovan ser vi hur en klass definieras med 
\mintinline{python}{class}-nyckelordet. Lägg märke till 
\mintinline{python}{self}-parametern i metoderna.

\begin{exercise}
  Vad tror du \mintinline{python}{self} betyder? Varför finns det som 
  första parameter i alla metoder?
\end{exercise}

\mintinline{python}{self} refererar till det specifika objektet (instansen) 
som metoden anropas på. Det är Pythons sätt att låta metoden veta vilket objekt 
den arbetar med och komma åt alla attributen (och de andra metoderna som finns 
definierade i klassen).

\begin{frame}[fragile]
  \begin{onlyenv}<presentation>
  \begin{block}{Objekt}
    \begin{itemize}
      \item Objekt (plural) är instanser av en klass.
    \end{itemize}
  \end{block}
  \end{onlyenv}

  \begin{minted}{python}
    objekt1 = Class("some value")
    objekt2 = Class("another value")
  \end{minted}
\end{frame}

Här skapar vi två olika objekt från samma klass. Båda objekten har samma 
struktur (samma metoder och attribut), men de är separata instanser som 
kan ha olika värden i sina attribut.


\subsection{Metoder och attribut}

\ltnote{%
  \textbf{Learning Objectives}: LO2 (Skapa klasser med attribut och
  metoder), LO3 (Förstå och använda parametern self)

  \textbf{Variation Pattern: Separation}

  \textbf{What varies}: The component type (attributes vs methods)

  \textbf{What remains invariant}: The class context (Person class) and
  the overall object structure

  \textbf{Critical aspects to discern}:
  \begin{itemize}
    \item \textbf{LO2}: Attributes are DATA (state), methods are BEHAVIOR
      (functions). By separating these concepts and showing them
      individually, students can discern the role of each.
    \item \textbf{LO3}: The \mintinline{python}{self} parameter appears
      in BOTH attributes and methods, helping students see it as the
      thread connecting all parts of an object.
  \end{itemize}

  \textbf{Why this separation works}: Following Marton \& Pang (2006),
  we isolate critical features from the whole. Instead of showing
  everything at once, we focus on attributes FIRST, then methods. This
  systematic variation reveals which aspects are invariant (the object
  instance via \mintinline{python}{self}) and which vary (data vs behavior).

  \textbf{Note}: This prepares for later FUSION when students must
  coordinate attributes and methods together in their own class designs.
}

Nu ska vi titta närmare på de två huvudkomponenterna i en klass: attribut
och metoder.

\begin{exercise}
  Vad är skillnaden mellan attribut och metoder i en klass?
  Försök att formulera dina egna definitioner innan du fortsätter läsa.
\end{exercise}

Attribut är data som objektet lagrar, medan metoder är funktioner som kan 
arbeta med denna data.

\begin{frame}[fragile]
  \begin{onlyenv}<presentation>
  \begin{block}{Attribut}
    \begin{itemize}
      \item Är data som tillhör objektet.
      \item Vanligtvis initierade i \mintinline{python}{__init__}.
    \end{itemize}
  \end{block}
  \end{onlyenv}

  \begin{minted}{python}
    class Class:
      def __init__(self, attr):
        self.__attr = attr
  \end{minted}
\end{frame}

\begin{exercise}
  I kodexemplet ovan, vilken metod används för att initiera attributen? 
  Vad tror du händer när vi skapar ett nytt objekt med 
  \mintinline{python}{Class(attribute)}?
\end{exercise}

Metoden \mintinline{python}{__init__} kallas automatiskt när vi skapar 
ett nytt objekt. Det är här vi sätter startvärden för objektets attribut. 
Låt oss se ett konkret exempel från vår \mintinline{python}{Person}-klass:

\begin{frame}[fragile]
  person.py \hrulefill
  \inputminted[linenos,lastline=15]{python}{examples/person.py}
\end{frame}

Här ser vi att \mintinline{python}{Person}-klassen har fem attribut: 
\begin{enumerate}
  \item \mintinline{python}{__first_name},
  \item \mintinline{python}{__last_name}, 
  \item \mintinline{python}{__birthday},
  \item \mintinline{python}{__address}, och 
  \item \mintinline{python}{__phone}.
\end{enumerate}
Alla lagras som privata attribut.

\begin{exercise}
  Vad är det som gör dem privata?
  Kan man göra publika attribut, hur?
\end{exercise}

Attributen är privata eftersom de börjar med dubbla understreck 
(\mintinline{python}{__}).
Om vi ville göra dem publika skulle vi helt enkelt inte använda några 
understreck alls.

\begin{frame}[fragile]
  \inputminted[highlightlines={7,21-22}]{python}{examples/public.py}
\end{frame}

Detta hade inte fungerat om vi hade skrivit \mintinline{python}{self.__value}
istället för \mintinline{python}{self.value}.
(Prova!)

\ltnote{%
  \textbf{Variation Pattern: Contrast}

  \textbf{What varies}: Attribute visibility (public
  \mintinline{python}{self.value} vs private
  \mintinline{python}{self.__value})

  \textbf{What remains invariant}: Everything else about the class
  structure

  \textbf{Relation to LO5 (encapsulation)}: By contrasting public and
  private attributes, students can discern WHEN and WHY to use
  encapsulation. The concrete example (direct access works vs doesn't
  work) makes the abstract principle tangible.

  \textbf{Note}: The exercise to ``try it'' is crucial---students
  experience the constraint themselves, which is more powerful than
  being told about it.
}

Nu ska vi titta på metoder---funktioner som tillhör objektet.

\begin{frame}[fragile]
  \begin{onlyenv}<presentation>
  \begin{block}{Metoder}
    \begin{itemize}
      \item Metoder är funktioner som tillhör objektet.
      \item Dessa används för att interagera med objektet.
    \end{itemize}
  \end{block}
  \end{onlyenv}

  \begin{minted}{python}
    class Class:
      def method(self):
        # do something object related
  \end{minted}
\end{frame}

Metoder är som funktioner, men de tillhör ett specifikt objekt och har 
tillgång till objektets attribut genom \mintinline{python}{self}.

\begin{exercise}
  Hur tror du vi kan läsa värdet på ett privat attribut som 
  \mintinline{python}{__first_name} om vi inte kan komma åt det direkt? 
  Varför skulle vi vilja ha privata attribut?
\end{exercise}

Svaret är att vi skapar metoder (ofta kallade 
\enquote{\foreignlanguage{english}{getters}}) för att läsa attributen. Detta ger 
oss kontroll över hur data läses och förhindrar ändringar.
Låt oss se exempel från \mintinline{python}{Person}-klassen:

  \dots
  \inputminted[autogobble=false,linenos,firstline=16,lastline=23]{python}{examples/person.py}

Här ser vi metoder som \mintinline{python}{get_name()} och

\section{Dundermetoder}

\ltnote{%
  \textbf{Learning Objective}: LO4 (Implementera dundermetoder)

  \textbf{Variation Pattern: Generalization}

  \textbf{What varies}: The specific dunder method
  (\mintinline{python}{__init__}, \mintinline{python}{__str__},
  \mintinline{python}{__lt__}, \mintinline{python}{__repr__}, etc.)

  \textbf{What remains invariant}: The pattern (double underscores,
  automatic invocation by Python, special behavior)

  \textbf{Critical aspect to discern}: Students should recognize that
  dunder methods form a PATTERN---they all follow the same naming
  convention and purpose (customizing object behavior), but each serves
  a different specific function.

  \textbf{Why generalization works}: By showing MULTIPLE dunder methods
  in the same context (Person class), students can see the invariant
  pattern across different contexts. This helps them recognize when to
  apply dunder methods in new situations.

  \textbf{Relation to LO4}: Students must not just memorize individual
  dunder methods but understand the general principle: ``When I want my
  objects to work with Python's built-in operations/functions, I implement
  the corresponding dunder method.''
}

Vi har redan sett några dundermetoder som \mintinline{python}{__init__}
och \mintinline{python}{__str__}. Python har många sådana \enquote{\foreignlanguage{english}{magic methods}}
som låter oss anpassa hur våra objekt beter sig i olika situationer.

\begin{frame}[fragile]
  person.py \hrulefill
  \inputminted[linenos,firstline=3,lastline=4]{python}{examples/person.py}
  \dots
  \inputminted[autogobble=false,linenos,firstline=21,lastline=23]{python}{examples/person.py}
\end{frame}

Vi såg tidigare att \mintinline{python}{__str__()} används för att 
konvertera objektet till en läsbar sträng. Detta är bara en av många 
dundermetoder som Python erbjuder.

\begin{exercise}

Här ser vi flera intressanta dundermetoder:
\begin{itemize}
  \item \mintinline{python}{__lt__} (\foreignlanguage{english}{less than}) används

  \item \mintinline{python}{__repr__} ger en mer teknisk representation av 
    objektet, ofta användbar för debugging.
    Ska inte användas på samma sätt som \mintinline{python}{__str__}.
    En tumregel är att utskriften från \mintinline{python}{__repr__} ska kunna 
    använadas för att särskilja objektet från andra objekt med \emph{exakt 
    samma värden på alla attribut}.
\end{itemize}

\begin{exercise}
  I koden ovan jämför \mintinline{python}{__lt__} födelsedagar.
  Då kunde vi använda \mintinline{python}{person1 < person2} för att jämföra 
  två personer.
  Kan vi även använda \mintinline{python}{person1 > person2}?
  Hur fungerar det i så fall?
\end{exercise}

Ja! Python använder automatiskt \mintinline{python}{__lt__} för att härleda 
\mintinline{python}{__gt__} (\foreignlanguage{english}{greater than}).
Faktum är att vi bara behöver definiera \mintinline{python}{__lt__}
(eller \mintinline{python}{__gt__})
och \mintinline{python}{__eq__} (\foreignlanguage{english}{equal}) för att få alla 
andra jämförelseoperatorer gratis.

\end{exercise}

\mintinline{python}{sorted()}.


\section{Arv}

\ltnote{%
  \textbf{Learning Objectives}: LO6 (Skapa underklasser med arv), LO7
  (Överlagra metoder och använda super()), LO8 (Avgöra när man ska använda
  arv kontra komposition)

  \textbf{Variation Pattern: Contrast + Separation}

  \textbf{First: Contrast two approaches}:
  \begin{enumerate}
    \item Code duplication (copy all Person code)
    \item Inheritance (extend Person)
  \end{enumerate}

  \textbf{Then: Separation of inheritance aspects}:
  \begin{itemize}
    \item Inherited methods (used as-is)
    \item Overridden methods (customized behavior)
    \item New methods (added functionality)
    \item Use of \mintinline{python}{super()} (accessing parent)
  \end{itemize}

  \textbf{Critical aspects to discern}:
  \begin{itemize}
    \item \textbf{LO6}: Inheritance creates an ``is-a'' relationship.
      PersonNick IS A Person with extra features. The contrast with
      code duplication shows WHY inheritance is valuable.
    \item \textbf{LO7}: By separating inherited vs overridden methods,
      students see that \mintinline{python}{super()} provides selective
      reuse---we keep what works, customize what doesn't.
    \item \textbf{LO8}: The contrast between ``is-a'' (inheritance) and
      ``has-a'' (composition) helps students choose appropriately.
  \end{itemize}

  \textbf{Why this works}: We start with the PROBLEM (avoiding code
  duplication) before introducing the SOLUTION (inheritance). This
  motivation-first approach creates a knowledge gap that inheritance
  fills.
}

Nu ska vi utforska ett av de mest kraftfulla koncepten i objektorienterad
programmering: arv (\foreignlanguage{english}{inheritance}).

\begin{exercise}
  Om du skulle skapa en \mintinline{python}{PersonNick}-klass som är
  precis som \mintinline{python}{Person} men också har ett smeknamn, hur skulle
  du göra det?
\end{exercise}

\ltnote{%
  Try-first pedagogy: Students consider how to solve the problem before
  seeing inheritance. Many will think of code duplication, which sets
  up the contrast with inheritance. This makes them appreciate the
  elegance of the inheritance solution.
}

Arv låter oss skapa nya klasser baserade på befintliga klasser, och utöka eller 
modifiera deras funktionalitet---helt utan kodupprepning.
Så istället för att kopiera all kod från \mintinline{python}{Person}, kan vi 
ärva från den och bara lägga till det nya vi behöver.

\begin{frame}[fragile]
  person\textunderscore nick.py \hrulefill
  \inputminted[linenos,firstline=3,lastline=8]{python}{examples/person_nick.py}
  \dots
  \inputminted[linenos,firstline=11,lastline=19]{python}{examples/person_nick.py}
\end{frame}

Notera syntaxen \mintinline{python}{class PersonNick(Person)}, detta betyder 
att \mintinline{python}{PersonNick} ärver från \mintinline{python}{Person}. Vi 
säger att \mintinline{python}{PersonNick} är en \emph{underklass} eller 
\emph{barnklass}
(\foreignlanguage{english}{subclass})
till \mintinline{python}{Person}, och \mintinline{python}{Person} är 
\emph{föräldraklass} 
(\foreignlanguage{english}{superclass})
till \mintinline{python}{PersonNick}.

\begin{exercise}
  Hur ska vi tilldela de attribut som \mintinline{python}{Person} redan har?
\end{exercise}

\begin{frame}[fragile]
  person\textunderscore nick.py \hrulefill
  \inputminted[linenos,firstline=9,lastline=10]{python}{examples/person_nick.py}
\end{frame}

I \mintinline{python}{__init__} använder vi \mintinline{python}{super()}
för att anropa föräldraklassens \mintinline{python}{__init__}-metod. Detta
initierar alla attribut från \mintinline{python}{Person}, och sedan lägger vi
till vårt nya attribut \mintinline{python}{__nick} som föräldern inte känner
till.

\ltnote{%
  \textbf{Variation Pattern: Separation}

  \textbf{What varies}: The initialization responsibilities (parent's
  attributes vs child's new attributes)

  \textbf{What remains invariant}: The initialization context
  (\mintinline{python}{__init__} method)

  \textbf{Relation to LO7}: The use of \mintinline{python}{super()}
  demonstrates selective reuse. We DON'T duplicate the parent's
  initialization code; we CALL it. This separation of concerns
  (parent handles its attributes, child handles its own) is a critical
  aspect of good OOP design.

  \textbf{Critical aspect}: \mintinline{python}{super()} is the bridge
  between child and parent, allowing controlled access to parent
  functionality.
}

\begin{exercise}
  Vilka metoder från \mintinline{python}{Person}-klassen kan
  \mintinline{python}{PersonNick} använda? Måste vi skriva om alla metoder?
\end{exercise}

Nej! \mintinline{python}{PersonNick} ärver automatiskt alla metoder från 
\mintinline{python}{Person}. Men vi kan också välja att \emph{ersätta} 
(överlagra, \foreignlanguage{english}{overload}) metoder om vi vill ändra deras 
beteende, vilket vi gjorde med \mintinline{python}{__init__()}.

\begin{frame}[fragile]
  \begin{onlyenv}<presentation>
  \begin{remark}
    \begin{itemize}
      \item Kan även byta ut funktionalitet.
    \end{itemize}
  \end{remark}
  \end{onlyenv}
  person\textunderscore nick.py \hrulefill
  \inputminted[linenos,firstline=21,lastline=29]{python}{examples/person_nick.py}
\end{frame}

Här har vi \emph{överlagrat} (\foreignlanguage{english}{overloaded}) metoden 
\mintinline{python}{get_name()}. Nu returnerar den smeknamnet om det finns, 
annars förnamnet. Den ursprungliga metoden från \mintinline{python}{Person} 
finns fortfarande kvar och kan nås via \mintinline{python}{super()}, vilket 
vi gör i metoden \mintinline{python}{get_full_name()}.

\begin{exercise}
  Varför tror du det är användbart att kunna anropa föräldraklassens metod 
  med \mintinline{python}{super()}? Ge ett exempel på när det skulle vara 
  praktiskt.
\end{exercise}

Det är användbart när vi vill \emph{utöka} beteendet snarare än att helt 
ersätta det. Vi kan köra föräldraklassens logik först, och sedan lägga till 
vår egen. Låt oss se hela exemplet:

\begin{frame}[fragile]
  person\textunderscore nick.py \hrulefill
  \inputminted[linenos,firstline=32]{python}{examples/person_nick.py}
\end{frame}

Här ser vi hur \mintinline{python}{PersonNick} används i praktiken. 
Objektet \mintinline{python}{person} har tillgång till alla metoder från 
både \mintinline{python}{PersonNick} och \mintinline{python}{Person}.

Låt oss sammanfatta konceptet arv:

\begin{frame}[fragile]
  \begin{onlyenv}<presentation>
  \begin{block}{Arv}
    \begin{itemize}
      \item En klass kan ärva en annan klass.
      \item Den kan då förbättra saker.
    \end{itemize}
  \end{block}
  \end{onlyenv}

  \begin{minted}{python}
    class Class:
      def method(self):
        # do something object related

    class Child(Class):
      def method(self):
        """ Better method """
        return super().method()**2
  \end{minted}
\end{frame}

I detta exempel ärver \mintinline{python}{Child} från 
\mintinline{python}{Class} och överskriver metoden 
\mintinline{python}{method()}. Den nya metoden anropar först den 
ursprungliga metoden via \mintinline{python}{super()}, och kvadrerar sedan 
resultatet.

\begin{exercise}
  Reflektera över fördelarna med arv: När skulle det vara lämpligt att
  använda arv? När skulle det vara bättre att skapa en helt ny klass istället?
\end{exercise}

\ltnote{%
  \textbf{Relation to LO8}: This reflection question asks students to
  generalize from the concrete example to abstract principles. By
  thinking about WHEN to use inheritance, they must discern the critical
  aspect: the type of relationship between classes.

  Try-first: Students reason about design choices before being given
  the rule. This active engagement helps them internalize the principle.
}

Arv är lämpligt när den nya klassen verkligen \enquote{är en} variant av
basklassen (\enquote{\foreignlanguage{english}{is-a}} relation). Till exempel är
\mintinline{python}{PersonNick} verkligen en \mintinline{python}{Person} med
extra funktionalitet. Om relationerna istället är \enquote{\foreignlanguage{english}{has-a}}
(till exempel en \mintinline{python}{Person} \enquote{har en}
\mintinline{python}{Address}), då är det bättre att använda komposition
(ett objekt som attribut) istället för arv.

\ltnote{%
  \textbf{Variation Pattern: Contrast}

  \textbf{What varies}: The relationship type (``is-a'' vs ``has-a'')

  \textbf{What remains invariant}: The goal of code reuse

  \textbf{Relation to LO8}: By contrasting these two relationships with
  concrete examples (PersonNick IS A Person, but Person HAS A Address),
  students can discern when each design pattern is appropriate. The
  contrast makes the critical aspect (relationship type) visible.

  \textbf{Why this works}: Both inheritance and composition achieve code
  reuse, but the TYPE of relationship determines which is appropriate.
  By keeping the goal invariant and varying the relationship, students
  can discern this critical distinction.
}
